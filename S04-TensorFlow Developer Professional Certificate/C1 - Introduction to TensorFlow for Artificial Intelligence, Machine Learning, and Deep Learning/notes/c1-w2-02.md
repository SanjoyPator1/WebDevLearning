# 2. An Introduction to Computer Vision

## What is Computer Vision?

**Computer vision** is the field of having a computer understand and label what is present in an image. While humans can instantly interpret visual content, programming computers to do this presents unique challenges.

## The Challenge of Programming Vision

### The Human-Computer Gap

When you look at an image, you can immediately identify objects like shirts, shoes, handbags, or coats. But **how would you program explicit rules for this recognition?**

The challenge becomes clear when you imagine explaining visual concepts to someone who has never seen clothing before - like an extraterrestrial visitor. How would you explain what makes a shoe different from a shirt? Writing explicit rules for such complex visual patterns is extremely difficult, if not impossible.

## The Machine Learning Solution

Instead of writing impossible rules, we can:

- Use **lots of pictures of clothing** with labels telling the computer what each picture shows
- Let the computer **figure out the patterns** that distinguish between different items
- Have the system learn the differences between shoes, shirts, handbags, and coats automatically

## Fashion MNIST Dataset

### Dataset Overview

**Fashion MNIST** provides the perfect training dataset for learning computer vision:

- **70,000 images** total across **10 different categories** of clothing
- Images are **28x28 pixels** - small enough for efficient processing
- **Grayscale images** to reduce data complexity
- Well-balanced dataset for machine learning

### Dataset Links

- **Official Repository**: [https://github.com/zalandoresearch/fashion-mnist](https://github.com/zalandoresearch/fashion-mnist)
- **Kaggle Dataset**: [https://www.kaggle.com/datasets/zalando-research/fashionmnist](https://www.kaggle.com/datasets/zalando-research/fashionmnist)
- **TensorFlow/Keras**: Built-in dataset (`tf.keras.datasets.fashion_mnist`)
- **PyTorch**: `torchvision.datasets.FashionMNIST`

### Technical Specifications

- **Image Dimensions**: 28×28 pixels
- **Color**: Grayscale (single channel)
- **Pixel Values**: 0-255 (one byte per pixel)
- **Storage per Image**: Only 784 bytes (28 × 28 pixels)
- **Data Split**:
  - Training set: 60,000 images
  - Test set: 10,000 images

### Why These Specifications Matter

**Small Size Benefits**:

- Less processing power required
- Faster training times
- Lower memory requirements
- Ideal for learning neural networks

**Information Retention**: Despite the small size, enough visual information remains to distinguish between different clothing categories. Even at 28×28 resolution, you can still clearly identify an ankle boot or differentiate between various clothing items.

**Grayscale Advantage**: Using grayscale instead of color reduces the data from 3 channels (RGB) to 1 channel, making it simpler while retaining essential shape and texture information.

## The 10 Fashion Categories

Each image belongs to one of these categories:

0. T-shirt/top
1. Trouser
2. Pullover
3. Dress
4. Coat
5. Sandal
6. Shirt
7. Sneaker
8. Bag
9. Ankle boot

## Why Fashion MNIST Over Original MNIST

Fashion MNIST serves as a **direct drop-in replacement** for the original MNIST handwritten digits dataset, but provides:

- More realistic real-world challenge
- Better benchmark for modern algorithms
- Same data structure and format as MNIST
- More complex visual patterns than simple digits

This dataset bridges the gap between the basic "Hello World" neural networks and real-world computer vision applications.

# 4. Writing Code to Load Training Data

## The Challenge: From Simple to Complex Data

In Week 1, we worked with just 6 pairs of numbers that could be easily hard-coded into our program. But now we're dealing with 70,000 images - a massive jump in data complexity. We can't possibly type out all these images manually, so we need a systematic way to load this data from storage.

This is where TensorFlow's built-in dataset functionality becomes invaluable. Fashion MNIST is so commonly used that it's included as a ready-to-use dataset with a simple API call.

## Loading the Dataset

The core loading operation is surprisingly simple:

```python
import tensorflow as tf

# Load the Fashion MNIST dataset
fashion_mnist = tf.keras.datasets.fashion_mnist
(train_images, train_labels), (test_images, test_labels) = fashion_mnist.load_data()
```

**What's happening here?**

First, we're accessing the Fashion MNIST dataset through TensorFlow's datasets collection. Then we call `load_data()`, which automatically downloads the dataset (if needed) and returns it in a structured format.

The function returns **four separate arrays** in a specific pattern:

- `train_images`: 60,000 images for training the neural network
- `train_labels`: 60,000 corresponding labels telling us what each training image is
- `test_images`: 10,000 images for testing the trained network
- `test_labels`: 10,000 corresponding labels for the test images

## Understanding the Train-Test Split Strategy

You might wonder: why split the data into two groups instead of using all 70,000 images for training?

This is a fundamental principle in machine learning called the **train-test split**. Here's why it's crucial:

**Training Data (60,000 images)**: These images are used to teach the neural network. The network sees these images and their labels repeatedly, learning to recognize patterns that distinguish between different clothing items.

**Testing Data (10,000 images)**: These images are kept separate and never shown to the network during training. After training is complete, we use these "unseen" images to test how well our network can recognize clothing items it has never encountered before.

Think of it like studying for an exam. You study with practice problems (training data), but the actual exam has different questions (testing data) to truly test your understanding.

## The Structure of Our Data

Let's examine what we actually get when we load the data:

```python
# Check the shapes of our data
print("Training images shape:", train_images.shape)      # (60000, 28, 28)
print("Training labels shape:", train_labels.shape)      # (60000,)
print("Test images shape:", test_images.shape)           # (10000, 28, 28)
print("Test labels shape:", test_labels.shape)           # (10000,)
```

The shape `(60000, 28, 28)` tells us we have 60,000 images, each measuring 28×28 pixels. The labels have shape `(60000,)` meaning we have 60,000 single numbers - one label for each image.

## Why Numbers Instead of Words for Labels?

When you look at an image of an ankle boot, you might expect the label to be the text "ankle boot". But instead, Fashion MNIST uses the number `9`. Why this seemingly counterintuitive choice?

**Reason 1: Computational Efficiency**
Computers process numbers much faster than text. When your neural network is processing thousands of images per second during training, using numbers instead of strings significantly speeds up the computation.

**Reason 2: Language Independence and Bias Reduction**
Using text labels like "ankle boot" would bias the dataset toward English speakers. By using numbers, the dataset becomes language-neutral. The number `9` can represent:

- "ankle boot" in English
- "踝靴" in Chinese
- "アンクルブーツ" in Japanese
- "Bróg rúitín" in Irish Gaelic
- Any term in any language

This makes the dataset more inclusive and globally accessible.

**Why normalize?** Neural networks generally work better with smaller numbers. Converting from the range 0-255 to 0-1 helps the network train more efficiently and consistently.

# 5. Labelling the Fashion MNIST Data

## Understanding Data Representation

In the previous lesson, we saw how Fashion MNIST data gets loaded into Python data structures that make neural network training straightforward. Let's dive deeper into understanding exactly how this data is structured and why these design choices matter.

### Image as Numerical Array

Each Fashion MNIST image is represented as a **28×28 array of grayscale values**. This means every image becomes a grid of 784 numbers (28 × 28 = 784), where each number represents the brightness of a single pixel:

- **0** = Pure black (darkest)
- **255** = Pure white (brightest)
- **1-254** = Various shades of gray

This numerical representation is fundamental because computers can only process numbers, not visual concepts. When you see an ankle boot, the computer sees 784 individual numbers arranged in a specific pattern.

### Labels as Numbers: The First Step in Bias Prevention

Perhaps the most important design decision in Fashion MNIST is using **numeric labels instead of text labels**. Each clothing item gets assigned a number from 0 to 9:

```
0 = T-shirt/top    5 = Sandal
1 = Trouser        6 = Shirt
2 = Pullover       7 = Sneaker
3 = Dress          8 = Bag
4 = Coat           9 = Ankle boot
```

### Why Numbers Matter: The Language Bias Problem

Using numeric labels is **the first crucial step in avoiding bias** in machine learning systems. Here's why this seemingly simple choice has profound implications:

#### The Problem with Text Labels

Imagine if Fashion MNIST used text labels like "ankle boot" instead of the number 9. This would create several problems:

**Language Exclusion**: The dataset would be biased toward English speakers, effectively excluding non-English speaking researchers and practitioners worldwide.

**Cultural Bias**: Clothing terminology varies significantly across cultures. What Americans call "sneakers," British people call "trainers," and other cultures have their own terms.

**Translation Complexity**: Every time someone wanted to use the dataset in a different language, they'd need to translate all the labels, creating potential for errors and inconsistencies.

#### The Solution: Universal Numbers

By using numbers, Fashion MNIST becomes **language-agnostic**:

- **Universal Understanding**: The number 9 means the same thing in every culture and language
- **No Translation Needed**: Researchers worldwide can use the same dataset without modification
- **Computational Efficiency**: Numbers are processed faster than text by computer systems
- **Reduced Bias**: No single language or culture is privileged over others

### Real-World Impact of This Decision

This design choice has significant real-world implications:

**Global Accessibility**: Researchers in China, Brazil, India, Germany, and anywhere else can use exactly the same dataset and compare their results directly.

**Fair Benchmarking**: Since everyone uses the same numeric labels, performance comparisons across different research groups are meaningful and fair.

**Inclusive AI Development**: The dataset doesn't inadvertently favor speakers of any particular language, making AI development more inclusive from the ground up.

## The Broader Context: Bias in Machine Learning

### Why Bias Prevention Matters

Fashion MNIST's numeric labeling addresses just one type of bias, but bias in machine learning is a much broader and critical issue that affects real people's lives.

#### Types of Bias in ML Systems

**Historical Bias**: When historical data reflects inequities that existed in the world at that time, such as housing data from the 1960s that contains discriminatory lending practices.

**Reporting Bias**: When the frequency of events captured in a dataset doesn't accurately reflect their real-world frequency.

**Selection Bias**: When dataset examples are chosen in ways that don't reflect real-world distribution, including coverage bias, non-response bias, and sampling bias.

**Group Attribution Bias**: The tendency to generalize what's true of individuals to entire groups they belong to.

#### Real-World Consequences

Bias can manifest in any part of a typical machine learning pipeline, from unrepresentative datasets to learned model representations to how results are presented to users. Errors from this bias can disproportionately impact some users more than others.

For example, consistently flagging non-toxic text comments from certain groups as "spam" or "high toxicity" in a moderation system leads to exclusion of those groups from conversation.

### Bias Detection and Mitigation Strategies

#### Proactive Data Auditing

When preparing data for model training, it's important to audit for potential sources of bias by looking for missing feature values, unexpected patterns, and data skew where certain groups may be under- or over-represented.

Key warning signs include:

- **Missing Values**: Large numbers of missing values for certain features might indicate under-represented characteristics
- **Data Skew**: When certain groups are over- or under-represented compared to real-world prevalence
- **Unexpected Patterns**: Anomalies that might indicate systematic collection issues

#### Evaluation Strategies

Aggregate performance metrics like precision, recall, and accuracy can mask poor performance on minority subsets, which can result in biased model predictions.

**Fairness Metrics Include**:

- **Demographic Parity**: Equal positive prediction rates across groups
- **Equality of Opportunity**: Equal true positive rates across groups
- **Counterfactual Fairness**: Ensuring that changing a sensitive attribute doesn't alter the model's prediction for equivalent examples

#### Technical Solutions

The TensorFlow Model Remediation Library provides utilities for bias mitigation techniques including MinDiff (balancing errors across data slices) and Counterfactual Logit Pairing (ensuring sensitive attributes don't alter predictions).

## Connecting Back to Fashion MNIST

### Why This Foundation Matters

Fashion MNIST's numeric labeling demonstrates **fairness by design** - building bias prevention into the fundamental structure of the dataset rather than treating it as an afterthought.

This principle applies beyond just labeling:

- **Balanced Classes**: Fashion MNIST has roughly equal numbers of examples for each clothing category
- **Standardized Format**: All images are the same size and format, preventing technical biases
- **Clear Documentation**: The dataset is well-documented so researchers understand its limitations

### Building on This Foundation

As you progress in machine learning, remember that Fashion MNIST's approach to bias prevention through numeric labels is just the beginning. Every decision in your ML pipeline - from data collection to model evaluation - is an opportunity to either introduce bias or prevent it.

The goal isn't just to build accurate models, but to build **fair and inclusive** systems that work equitably for all users.

# 6. Coding a Computer Vision Neural Network

## From Simple to Complex: Neural Network Evolution

In Week 1, we built a neural network with just **one layer** using `tf.keras.Sequential`. Now we're building a much more sophisticated network with **three layers** to handle computer vision tasks. This represents a significant jump in complexity, but the fundamental principles remain the same.

## The Three-Layer Architecture

Let's examine the complete neural network code:

```python
model = tf.keras.Sequential([
    tf.keras.Input(shape=(28, 28)),
    tf.keras.layers.Flatten(),
    tf.keras.layers.Dense(128, activation='relu'),
    tf.keras.layers.Dense(10, activation='softmax')
])
```

This simple code creates a powerful neural network. Let's understand what each layer does and why it's designed this way.

## Layer-by-Layer Breakdown

### Layer 1: Input Layer - Setting Expectations

```python
tf.keras.Input(shape=(28, 28))
```

**What it does**: This layer doesn't perform any computation - it simply tells the network what size data to expect.

**Why (28, 28)?** Our Fashion MNIST images are 28×28 pixels, so we're specifying that this neural network should expect data in exactly this format. This acts like a "contract" - the network knows exactly what input structure to prepare for.

**Important principle**: Always match your input layer to your actual data dimensions. If your images were 32×32, you'd use `shape=(32, 32)`.

### Layer 2: Flatten Layer - Reshaping the Data

```python
tf.keras.layers.Flatten()
```

**What it does**: Takes the 28×28 square (2D array) and converts it into a simple linear array (1D array) of 784 values.

**Why is this necessary?** Neural networks, specifically Dense layers, expect input as a 1D array. Think of it as unrolling a grid:

```
28×28 grid:     →     784-length array:
[1,2,3]               [1,2,3,4,5,6,7,8,9]
[4,5,6]
[7,8,9]
```

**Mathematical transformation**: 28 × 28 = 784 individual pixel values arranged in a straight line.

```ascii
Before Flatten (28×28):
┌─────────────────────────┐
│ █ █ ░ ░ █ █ ░ ... (28)  │
│ █ ░ ░ █ ░ █ ░ ...       │
│ ░ █ ░ ░ █ ░ █ ...       │
│ ...                     │
│ (28 rows total)         │
└─────────────────────────┘

After Flatten (784×1):
┌─┬─┬─┬─┬─┬─┬─┬─────┬───┐
│█│█│░│░│█│█│░│ ... │784│
└─┴─┴─┴─┴─┴─┴─┴─────┴───┘
```

### Layer 3: Hidden Layer - The Pattern Detector

```python
tf.keras.layers.Dense(128, activation='relu')
```

**What it does**: This is where the "magic" happens. This hidden layer has **128 neurons**, each acting like a pattern detector.

**Think of neurons as variables**: Consider these 128 neurons as variables x₁, x₂, x₃, ..., x₁₂₈ in a complex mathematical function.

**The mathematical concept**: Each neuron receives all 784 pixel values and performs a calculation like:

$$\text{neuron}_1 = w_1 \times \text{pixel}_1 + w_2 \times \text{pixel}_2 + \ldots + w_{784} \times \text{pixel}_{784} + b$$

**Why 128 neurons?** This is a design choice that provides enough "computing power" to detect patterns in clothing images without being too complex. You can experiment with different numbers (64, 256, etc.).

### Layer 4: Output Layer - Making the Final Decision

```python
tf.keras.layers.Dense(10, activation='softmax')
```

**Why exactly 10 neurons?** Because we have exactly **10 classes of clothing** in Fashion MNIST. This is a fundamental rule: **the number of output neurons must match the number of classes**.

**The matching principle**:

- 10 clothing categories → 10 output neurons
- If you had 5 categories → 5 output neurons
- If you had 100 categories → 100 output neurons

## The Mathematical Magic: From Pixels to Predictions

### Understanding the Complex Function

The neural network essentially learns a complex function that transforms 784 pixel values into a clothing category prediction. Here's the conceptual mathematical flow:

**Input**: 784 pixel values representing an ankle boot  
**Hidden Layer Processing**: 128 different pattern detectors  
**Output**: The number 9 (representing "ankle boot")

### The Weight Learning Process

The network learns by adjusting **weights** (w values). Think of it like the simple linear equation from Week 1:

**Week 1**: `y = 2x - 1` (where 2 was the weight)  
**Week 2**: `y = w₁×x₁ + w₂×x₂ + w₃×x₃ + ... + w₁₂₈×x₁₂₈`

The network figures out the optimal values for all these weights through training with the 60,000 examples.

### Visual Representation

```ascii
Input Layer (784 values)    Hidden Layer (128)    Output Layer (10)
┌───┐                      ┌───┐                 ┌───┐
│ █ │──────────────────────│x₁ │─────────────────│ 0 │ T-shirt
│ ░ │──┐             ┌─────│x₂ │──┐         ┌────│ 1 │ Trouser
│ █ │──┼─────────────┼─────│x₃ │──┼─────────┼────│ 2 │ Pullover
│...│  │    (every   │     │...|  │  (all   │    │...|
│ ░ │  │     pixel   │     │x₁₂₈│ │ hidden  │    │ 8 │ Bag
│ █ │──┘   connects  └─────│   │──┘  to all │    │ 9 │ Ankle boot ★
└───┘     to every         └───┘     output)└────└───┘
                                              Predicted: 9
```

## The Learning Process: How Weights Are Discovered

### The Impossible Task Made Possible

**Human limitation**: You couldn't manually create rules to distinguish between all 70,000 Fashion MNIST images and assign them to the correct categories.

**Neural network solution**: By processing all 60,000 training examples repeatedly, the network automatically discovers the optimal weight values that correctly map pixel patterns to clothing categories.

### Connection to Week 1

**Week 1 analogy**: In our simple example, we learned that `y = 2x - 1` by seeing examples like:

- When x=1, y=1
- When x=2, y=3
- When x=3, y=5

**Week 2 scaling**: Now we're doing the same thing but with:

- 784 input values instead of 1
- 128 hidden pattern detectors
- 10 possible outputs instead of 1
- 60,000 examples instead of 6

## Network Architecture Flexibility

### Experimentation Possibilities

The beauty of this architecture is that you can experiment with different configurations:

**Changing hidden layer size**:

```python
Dense(64, activation='relu')    # Fewer neurons - simpler patterns
Dense(256, activation='relu')   # More neurons - more complex patterns
Dense(512, activation='relu')   # Even more neurons - very complex patterns
```

**Adding more layers**:

```python
tf.keras.Sequential([
    tf.keras.Input(shape=(28, 28)),
    tf.keras.layers.Flatten(),
    tf.keras.layers.Dense(128, activation='relu'),
    tf.keras.layers.Dense(64, activation='relu'),   # Additional hidden layer
    tf.keras.layers.Dense(10, activation='softmax')
])
```

### Design Trade-offs

**Fewer neurons (e.g., 32)**:

- ✅ Trains faster
- ✅ Uses less memory
- ❌ May miss complex patterns

**More neurons (e.g., 512)**:

- ✅ Can detect more complex patterns
- ❌ Takes longer to train
- ❌ May overfit to training data

## Practical Implementation Tips

### Essential Rules to Remember

1. **Input shape must match data**: If your images are 32×32, use `shape=(32, 32)`
2. **Output neurons must match classes**: 10 clothing types = 10 output neurons
3. **Flatten is necessary**: Dense layers need 1D input, images are 2D
4. **Start simple**: Begin with one hidden layer, then experiment

### Common Mistakes to Avoid

**Shape mismatch**:

```python
# Wrong: Data is 28×28 but specified 32×32
tf.keras.Input(shape=(32, 32))  # ❌

# Correct: Match your actual data
tf.keras.Input(shape=(28, 28))  # ✅
```

**Wrong output size**:

# 8. Using Callbacks to Control Training

## The Hard-Coding Problem

When experimenting with neural networks, programmers frequently ask: "Why do I always have to hard-code the number of epochs? How can I stop training when I reach the performance I want instead of guessing how many epochs to run?"

This is a common frustration when you're trying to find the optimal training duration. You might set epochs=10 and find the model could have stopped at epoch 7, or set epochs=5 and realize the model needed more training time.

## The Callback Solution

TensorFlow provides an elegant solution through **callbacks** - functions that can monitor training progress and make decisions about when to stop. Instead of blindly running for a fixed number of epochs, callbacks let you set intelligent stopping conditions.

### What Are Callbacks?

**Callbacks** are functions that get executed at specific points during training. They can:

- Monitor training metrics after each epoch
- Make decisions based on current performance
- Stop training early when conditions are met
- Save models, log data, or perform other actions

Think of callbacks like a coach watching a player practice - they observe performance and decide when the player has practiced enough.

## Implementing a Custom Callback

### The Basic Structure

Here's how to create a custom callback that stops training when loss reaches a target:

```python
class myCallback(tf.keras.callbacks.Callback):
    def on_epoch_end(self, epoch, logs=None):
        if logs['loss'] < 0.4:
            print('Loss is low so cancelling training!')
            self.model.stop_training = True
```

### Understanding the Components

**Class Inheritance**:

```python
class myCallback(tf.keras.callbacks.Callback):
```

Your callback must inherit from `tf.keras.callbacks.Callback` to access the callback functionality.

**The `on_epoch_end` Method**:

```python
def on_epoch_end(self, epoch, logs=None):
```

This method gets called automatically at the end of each epoch. It receives:

- `epoch`: The current epoch number
- `logs`: A dictionary containing training metrics

**The Logs Object**:
The `logs` parameter contains valuable training information:

```python
logs['loss']           # Current training loss
logs['accuracy']       # Current training accuracy
logs['val_loss']       # Validation loss (if validation data provided)
logs['val_accuracy']   # Validation accuracy (if validation data provided)
```

**Stopping Training**:

```python
self.model.stop_training = True
```

Setting this flag tells TensorFlow to stop the training loop after the current epoch completes.

## Using the Callback in Training

### Integration with model.fit()

To use your callback, pass it to the `callbacks` parameter:

```python
# Create an instance of your callback
callback = myCallback()

# Use it in training
model.fit(training_images, training_labels,
          epochs=50,  # Set high, let callback decide when to stop
          callbacks=[callback])
```

# 9. Understanding Train/Validation/Test Data Splits

## The Data Split Confusion

A critical concept that often confuses beginners is the difference between validation data and test data, especially when looking at Fashion MNIST examples where the test set is commonly used for validation during training.

## What Actually Happens in Our Code

### The Current Approach (Educational)

In the Fashion MNIST tutorials and our notebook, you'll see this pattern:

```python
# Training uses 60,000 images
model.fit(train_images, train_labels,
          validation_data=(test_images, test_labels))  # Using test set!
```

**What's happening:**

- **Training data**: 60,000 Fashion MNIST training images
- **Validation data**: 10,000 Fashion MNIST test images (used during training)
- **Final evaluation**: Same 10,000 test images (used after training)

This means the "test" set is actually being used twice - once as validation during training, and once for final evaluation.

## The Problem with This Approach

### Data Leakage Issue

Using the test set for validation creates **data leakage** because:

- The model indirectly "sees" the test data during training through validation metrics
- Early stopping and hyperparameter decisions are influenced by test set performance
- The final evaluation isn't truly unbiased since the model was optimized on this data

### Why Educational Examples Do This

Fashion MNIST tutorials use test data for validation because:

1. **Simplicity**: Easier to explain with pre-split data
2. **Benchmark consistency**: Allows comparison with published results
3. **Educational focus**: Emphasis on learning concepts rather than perfect ML practices

## The Correct Approach: Proper Three-Way Split

### How It Should Be Done

```python
# Proper data splitting from the 60,000 training images
total_train_size = 60000
train_size = int(0.8 * total_train_size)  # 48,000 for training
val_size = total_train_size - train_size   # 12,000 for validation

# Split the original training data
train_images_final = train_images[:train_size]
train_labels_final = train_labels[:train_size]

val_images = train_images[train_size:]
val_labels = train_labels[train_size:]

# Keep test set completely separate
# test_images and test_labels remain untouched until final evaluation
```

### The Three-Set Purpose

**Training Set (48,000 images)**:

- Used for actual model learning
- Model sees this data and updates weights based on it
- Gradients are calculated from this data

**Validation Set (12,000 images)**:

- Used during training for performance monitoring
- Triggers early stopping when validation performance stops improving
- Used for hyperparameter tuning and model selection
- Never used for weight updates

**Test Set (10,000 images)**:

- Used only once at the very end
- Provides unbiased performance estimate
- Should never influence training decisions

## Mathematical Representation

The proper data flow should be:

$$
\text{Original Training Data} \rightarrow \begin{cases}
\text{Training Set (80\%)} \rightarrow \text{Model Training} \\
\text{Validation Set (20\%)} \rightarrow \text{Performance Monitoring}
\end{cases}
$$

$$\text{Test Set} \rightarrow \text{Final Evaluation Only}$$

## Practical Implementation

### Creating Proper Splits

```python
def create_proper_splits(train_images, train_labels, val_split=0.2):
    """
    Creates proper train/validation split from training data.

    Args:
        train_images: Original training images (60,000)
        train_labels: Original training labels (60,000)
        val_split: Fraction to use for validation (default: 0.2)

    Returns:
        Properly split training and validation sets
    """
    # Calculate split indices
    total_samples = len(train_images)
    val_samples = int(total_samples * val_split)
    train_samples = total_samples - val_samples

    # Create splits
    train_images_split = train_images[:train_samples]
    train_labels_split = train_labels[:train_samples]

    val_images_split = train_images[train_samples:]
    val_labels_split = train_labels[train_samples:]

    print(f"Training samples: {len(train_images_split)}")
    print(f"Validation samples: {len(val_images_split)}")

    return (train_images_split, train_labels_split,
            val_images_split, val_labels_split)
```

### Training with Proper Splits

```python
# Create proper splits
(train_imgs, train_lbls,
 val_imgs, val_lbls) = create_proper_splits(train_images_norm, train_labels)

# Train with proper validation
model.fit(train_imgs, train_lbls,
          validation_data=(val_imgs, val_lbls),  # Proper validation set
          epochs=10)

# Final evaluation on completely unseen test set

```

## When Each Approach Is Appropriate

### Educational/Tutorial Context

- Using test set for validation is acceptable when learning concepts
- Focus is on understanding neural networks, not perfect ML practices
- Benchmark datasets like Fashion MNIST are well-established

### Real-World Projects

- Always create proper train/validation/test splits
- Never use test data for any training decisions
- Validation set should be representative of the problem domain

## Key Takeaways

1. **Fashion MNIST tutorials** use test data as validation for simplicity
2. **Real ML projects** should never touch test data until final evaluation
3. **Validation data** should come from splitting the training set
4. **Test set performance** should be reported only once at the project's end
5. **Data leakage** occurs when test data influences training decisions

## Red Flags to Watch For

- Using test set for hyperparameter tuning
- Multiple evaluations on test set during development
- Making architectural decisions based on test performance
- Early stopping based on test set metrics

Understanding this distinction is crucial for developing robust machine learning models that generalize well to truly unseen data.
