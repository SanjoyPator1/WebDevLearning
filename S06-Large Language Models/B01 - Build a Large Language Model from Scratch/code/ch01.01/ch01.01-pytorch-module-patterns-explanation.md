## 0 — Why This Notebook Exists

Chapter 1 introduced `nn.Linear` and `nn.Sequential` just enough to build a small classifier and train it. That was enough to get a feedforward network running, but it skips over the questions that come up the moment you try to build something like GPT-2's feedforward stack — the `ExampleDeepNeuralNetwork` you'll meet again in Chapter 4 §12–13:

```python
class ExampleDeepNeuralNetwork(nn.Module):
    def __init__(self, layer_sizes, use_shortcut):
        super().__init__()
        self.use_shortcut = use_shortcut
        self.layers = nn.ModuleList([
            nn.Sequential(nn.Linear(layer_sizes[0], layer_sizes[1]), GELU()),
            nn.Sequential(nn.Linear(layer_sizes[1], layer_sizes[2]), GELU()),
            nn.Sequential(nn.Linear(layer_sizes[2], layer_sizes[3]), GELU()),
            nn.Sequential(nn.Linear(layer_sizes[3], layer_sizes[4]), GELU()),
            nn.Sequential(nn.Linear(layer_sizes[4], layer_sizes[5]), GELU()),
        ])
```

Three things about this snippet are not obvious from Chapter 1 alone: why the outer container is a `ModuleList` and not a plain Python list, why each entry is a `Sequential` rather than a bare `Linear`, and what `use_shortcut` does to the gradients flowing backward through five stacked layers. This notebook answers all three, plus the weight-initialization and parameter-counting questions that come up the moment you start inspecting a model this size.

## 1 — `nn.Linear` Internals

**Summary.** `nn.Linear(in_features, out_features)` stores a weight matrix and a bias vector, and its `forward` is one affine transform: $y = xW^T + b$.

**The intuition.** A linear layer is a lookup of weighted combinations — every output feature is its own weighted sum of every input feature, plus an offset. Stacking these (with nonlinearities between them) is how a network learns which combinations of input features matter.

**The math.** For a single input vector $x \in \mathbb{R}^{d_{in}}$, weight matrix $W \in \mathbb{R}^{d_{out} \times d_{in}}$, and bias $b \in \mathbb{R}^{d_{out}}$:

$$y = xW^T + b, \qquad y \in \mathbb{R}^{d_{out}}$$

PyTorch stores $W$ with shape `(out_features, in_features)` — *not* `(in_features, out_features)`. That's why the forward pass transposes it.

**Dry-run.** Take `nn.Linear(3, 2)` on a single input row $x = [1, 2, 3]$, with weights chosen by hand:

```
W = [[ 0.1,  0.2,  0.3],      # row 0 → output feature 0
     [-0.1,  0.0,  0.1]]     # row 1 → output feature 1
b = [0.01, 0.02]

y[0] = x · W[0] + b[0] = (1*0.1 + 2*0.2 + 3*0.3) + 0.01 = 1.4 + 0.01 = 1.41
y[1] = x · W[1] + b[1] = (1*-0.1 + 2*0.0 + 3*0.1) + 0.02 = 0.2 + 0.02 = 0.22

y = [1.41, 0.22]
```

**The code** — manual replica vs. `nn.Linear`, same weights:

```python
import torch
import torch.nn as nn

torch.manual_seed(42)

x = torch.tensor([[1.0, 2.0, 3.0]])  # shape: (1, 3) -> (batch=1, in_features=3)

W = torch.tensor([[0.1, 0.2, 0.3],
                   [-0.1, 0.0, 0.1]])  # shape: (2, 3) -> (out_features=2, in_features=3)
b = torch.tensor([0.01, 0.02])         # shape: (2,)

y_manual = x @ W.T + b
print("Manual y:", y_manual)
# Manual y: tensor([[1.4100, 0.2200]])

linear = nn.Linear(3, 2)
with torch.no_grad():
    linear.weight.copy_(W)
    linear.bias.copy_(b)

y_module = linear(x)
print("nn.Linear y:", y_module)
# nn.Linear y: tensor([[1.4100, 0.2200]], grad_fn=<AddmmBackward0>)

print("Match:", torch.allclose(y_manual, y_module))
# Match: True
```

**The gotcha.** `linear.weight.shape` is `(out_features, in_features)`. People who forget the transpose and write `x @ W + b` directly get a shape-mismatch error the instant `in_features != out_features`.

## 2 — Weight Initialization

**The problem it solves.** A freshly created `nn.Linear` doesn't start at zero — if every layer in a deep stack started with identical or zero weights, every neuron in a layer would compute the same gradient and the network could never break that symmetry. Initialization also controls how activation variance grows or shrinks as it passes through many layers; pick it badly and a 5-layer network's activations either vanish toward zero or explode, well before training even starts.

**The default.** `nn.Linear`'s default initializer is `kaiming_uniform_` with a gain tuned for `ReLU`-family activations: weights are drawn uniformly from $\left[-\frac{1}{\sqrt{d_{in}}}, \frac{1}{\sqrt{d_{in}}}\right]$, scaled by a gain factor. The intent is to keep the variance of activations roughly constant from one layer to the next.

**The math — why $1/\sqrt{d_{in}}$.** If $x_i$ are i.i.d. with variance $\sigma_x^2$ and weights $w_i$ are i.i.d. with variance $\sigma_w^2$, the output of one neuron, $y = \sum_{i=1}^{d_{in}} w_i x_i$, has variance:

$$\text{Var}(y) = d_{in} \cdot \sigma_w^2 \cdot \sigma_x^2$$

To keep $\text{Var}(y) \approx \sigma_x^2$ (i.e. the variance doesn't grow with $d_{in}$), you need $\sigma_w^2 \approx 1/d_{in}$ — hence weight scale $\propto 1/\sqrt{d_{in}}$. This is the same reasoning behind dividing attention scores by $\sqrt{d_k}$ in Chapter 3 — it's the same "control the variance" problem showing up again.

**Dry-run.** Five stacked `Linear(20, 20)` layers, no activation, comparing two initializations on the same random input $x$ with $\text{Var}(x) \approx 1$:

```
Init A: weights ~ N(0, 1)            (too large — ignores 1/sqrt(d_in))
  layer 1 output var: ~20
  layer 2 output var: ~400
  layer 5 output var: ~3,200,000   <- exploding

Init B: weights ~ N(0, 1/20)         (Xavier/He-style scaling)
  layer 1 output var: ~1.0
  layer 2 output var: ~1.0
  layer 5 output var: ~1.0          <- stable
```

**The code:**

```python
import torch
import torch.nn as nn

torch.manual_seed(42)

def make_stack(init_std):
    layers = [nn.Linear(20, 20, bias=False) for _ in range(5)]
    for layer in layers:
        nn.init.normal_(layer.weight, mean=0.0, std=init_std)
    return layers

x = torch.randn(1, 20)  # Var(x) ~ 1

for label, std in [("too large (std=1.0)", 1.0), ("Xavier-style (std=1/sqrt(20))", 1.0 / (20 ** 0.5))]:
    out = x
    print(f"\n{label}")
    for i, layer in enumerate(make_stack(std)):
        out = layer(out)
        print(f"  after layer {i+1}: var={out.var().item():.4f}")
```

```
too large (std=1.0)
  after layer 1: var=20.4428
  after layer 2: var=590.5243
  after layer 3: var=12556.4502
  after layer 4: var=195701.2812
  after layer 5: var=3337619.7500

Xavier-style (std=1/sqrt(20))
  after layer 1: var=1.2812
  after layer 2: var=0.7627
  after layer 3: var=0.7573
  after layer 4: var=0.8247
  after layer 5: var=0.9779
```

**The gotcha.** `nn.init.*` functions mutate the tensor in place and must be called inside `torch.no_grad()` (or via the `_`-suffixed in-place functions directly, which already skip autograd tracking) — applying them to a tensor that's part of an active computation graph raises an error or silently corrupts gradients.

## 3 — `nn.Sequential` — Chaining Layers, and Where It Breaks

**Recap.** `nn.Sequential(layer1, layer2, ...)` calls each layer in order, feeding each output to the next input. It supports indexing (`seq[0]`) and iteration, and registers every layer's parameters automatically.

**Where it breaks.** `Sequential.forward` is fixed: `x = layer_n(...layer_1(x))`. There is no hook for "also keep a copy of `x` from three layers ago and add it back in" — a residual/shortcut connection — because `Sequential` only ever sees one tensor flowing through a straight line. The moment your forward pass needs to be anything other than a straight pipe — branching, skipping, concatenating — `Sequential` cannot express it, full stop. The next two sections (`ModuleList`, `ModuleDict`) exist specifically to register submodules' parameters *without* forcing that straight-pipe forward logic on you.

```
nn.Sequential — forced shape:

   x ──▶ [layer 1] ──▶ [layer 2] ──▶ [layer 3] ──▶ out
                                                     ^
                                          no way to also feed x in here
```

## 4 — `nn.ModuleList` and the Hidden-Parameters Bug

**The problem it solves.** You want a *list* of submodules (so you can loop over them, index them, vary their count), but you also want their parameters to show up in `.parameters()`, move correctly with `.to(device)`, and get saved by `state_dict()`. A plain Python list does none of this — `nn.Module` only tracks attributes it recognizes as submodules, and a `list` doesn't register as one.

**Dry-run — the bug.**

```python
import torch.nn as nn

class BrokenStack(nn.Module):
    def __init__(self):
        super().__init__()
        self.layers = [nn.Linear(4, 4) for _ in range(3)]  # plain Python list

class FixedStack(nn.Module):
    def __init__(self):
        super().__init__()
        self.layers = nn.ModuleList([nn.Linear(4, 4) for _ in range(3)])

broken = BrokenStack()
fixed = FixedStack()

print("Broken param count:", sum(p.numel() for p in broken.parameters()))
print("Fixed param count: ", sum(p.numel() for p in fixed.parameters()))
```

```
Broken param count: 0
Fixed param count:  60
```

The three `Linear(4, 4)` layers in `BrokenStack` are real, working modules — calling them directly still works — but `broken.parameters()` cannot see them, so an optimizer built from `broken.parameters()` would silently train nothing, and `broken.to("cuda")` would silently leave those layers on the CPU. This is a bug with no error message, which is exactly what makes it dangerous.

**What `nn.ModuleList` actually is.** It's a container that holds submodules and supports `len()`, indexing, and iteration like a list — but every element you put in it gets registered as a proper child module, the same way assigning `self.fc = nn.Linear(...)` would. It does **not** define a `forward` for you; you still write the loop yourself:

```python
class FixedStack(nn.Module):
    def __init__(self):
        super().__init__()
        self.layers = nn.ModuleList([nn.Linear(4, 4) for _ in range(3)])

    def forward(self, x):
        for layer in self.layers:
            x = layer(x)        # you control exactly what happens between layers
        return x
```

This is the key difference from `Sequential`: because you write the loop body, you're free to add a residual connection, skip a layer conditionally, or concatenate — none of which `Sequential` can do.

## 5 — `nn.ModuleDict` — Named Submodules

**The problem it solves.** Sometimes you don't want an ordered list, you want named branches — e.g. a model with a `"classification_head"` and a `"regression_head"` sharing a trunk, or a transformer block holding `"attention"` and `"feedforward"` sublayers you want to address by name rather than index.

```python
class MultiHead(nn.Module):
    def __init__(self):
        super().__init__()
        self.heads = nn.ModuleDict({
            "classification": nn.Linear(16, 10),
            "regression": nn.Linear(16, 1),
        })

    def forward(self, x, head_name):
        return self.heads[head_name](x)

model = MultiHead()
x = torch.randn(2, 16)
print("classification output shape:", model(x, "classification").shape)
print("regression output shape:", model(x, "regression").shape)
```

```
classification output shape: torch.Size([2, 10])
regression output shape: torch.Size([2, 1])
```

Like `ModuleList`, `ModuleDict` only solves the registration problem — `.parameters()`, `.to(device)`, `state_dict()` all work correctly — and you still write the dispatch logic in `forward` yourself.

## 6 — Decision Guide: Which Container Do I Reach For?

| Container | Forward logic | Indexing | When to use |
|---|---|---|---|
| `nn.Linear` | N/A — it *is* the layer | — | One affine transform |
| `nn.Sequential` | Fixed straight-line, provided for you | Integer (`seq[0]`) | Strictly sequential stack, no branching, no residuals |
| `nn.ModuleList` | You write it | Integer, iterable, `len()` | Variable number of submodules, need indexing/looping, need residuals/branching/skipping |
| `nn.ModuleDict` | You write it | String key | Named submodules accessed by name rather than position |
| Plain Python `list`/`dict` of modules | You write it | — | **Never**, if the modules need gradients tracked — they silently vanish from `.parameters()` |

```
                "Do I just need to register submodules so
                 .parameters() / .to() / state_dict() work?"
                                  │
              ┌───────────────────┴───────────────────┐
              │                                        │
        straight pipe,                          need to write a
        no branching/skip?                      custom forward loop?
              │                                        │
              ▼                                        ▼
        nn.Sequential                    indexed/iterable? ── nn.ModuleList
                                          named/keyed?     ── nn.ModuleDict
```

## 7 — Combining `ModuleList` of `Sequential` Blocks + Shortcuts

Now the snippet from §0 should read differently. `ExampleDeepNeuralNetwork` needs:

1. A variable number of blocks (`layer_sizes` can be any length) → rules out hardcoding five `self.layer1`, `self.layer2`, ... attributes → needs `ModuleList`.
2. Each block is itself a fixed two-step pipe, `Linear` then `GELU`, with no branching inside the block → `Sequential` is the right tool *inside* each block.
3. The outer `forward` needs to conditionally add `x` back to each block's output → that conditional logic can only live in a hand-written loop → confirms the outer container must be `ModuleList`, not `Sequential`.

```
ExampleDeepNeuralNetwork.layers  (an nn.ModuleList, 5 entries)

  layers[0] = nn.Sequential(Linear(3,3), GELU())
  layers[1] = nn.Sequential(Linear(3,3), GELU())
  layers[2] = nn.Sequential(Linear(3,3), GELU())
  layers[3] = nn.Sequential(Linear(3,3), GELU())
  layers[4] = nn.Sequential(Linear(3,1), GELU())

forward(x):
    for layer in self.layers:
        layer_output = layer(x)
        if self.use_shortcut and x.shape == layer_output.shape:
            x = x + layer_output     # residual add — impossible inside nn.Sequential
        else:
            x = layer_output
    return x
```

**Why the shortcut matters for gradients.** Without the shortcut, the gradient reaching an early layer during backpropagation is a product of the local gradients of every later layer — five `GELU` derivatives and five weight matrices multiplied together. Each `GELU` derivative is at most around 0.4–0.5 in the regions away from its linear stretch, and weights initialized with small variance compound the shrinkage. By layer 1, the gradient signal can be a small fraction of what it started as — the same vanishing-gradient mechanism that motivated LayerNorm and careful init in Chapter 4 §13.

With the shortcut, the gradient has a direct additive path back to every earlier layer (because $\frac{\partial}{\partial x}(x + f(x)) = 1 + f'(x)$ — there's always a clean "+1" term, no matter how small $f'(x)$ gets), so it doesn't have to survive multiplying through every intermediate layer to reach the start of the network. Chapter 4 §12–13 measures this directly: gradient means at the first layer differ by roughly three orders of magnitude with vs. without the shortcut.

## 8 — Parameter Counting

**Why bother.** Once a model has dozens of submodules, "how big is this thing" and "which layer holds most of the parameters" stop being questions you can answer by eyeballing the class definition.

**The tools.** `model.named_parameters()` yields `(name, parameter)` pairs where `name` encodes the path through the module tree (e.g. `"layers.2.0.weight"` means: third entry of `self.layers`, first submodule of that `Sequential`, its `weight`). `parameter.numel()` gives the element count of a single tensor; `parameter.requires_grad` tells you if it's trainable or frozen.

```python
def count_parameters(model):
    total = 0
    trainable = 0
    print(f"{'name':35s} {'shape':18s} {'count':>10s} {'trainable':>10s}")
    for name, param in model.named_parameters():
        n = param.numel()
        total += n
        if param.requires_grad:
            trainable += n
        print(f"{name:35s} {str(tuple(param.shape)):18s} {n:>10d} {str(param.requires_grad):>10s}")
    print(f"\nTotal parameters:     {total:,}")
    print(f"Trainable parameters: {trainable:,}")
    return total, trainable
```

Run against a 5-block `ExampleDeepNeuralNetwork([3, 3, 3, 3, 3, 1], use_shortcut=True)`:

```
name                                shape                   count  trainable
layers.0.0.weight                   (3, 3)                      9       True
layers.0.0.bias                     (3,)                        3       True
layers.1.0.weight                   (3, 3)                      9       True
layers.1.0.bias                     (3,)                        3       True
layers.2.0.weight                   (3, 3)                      9       True
layers.2.0.bias                     (3,)                        3       True
layers.3.0.weight                   (3, 3)                      9       True
layers.3.0.bias                     (3,)                        3       True
layers.4.0.weight                   (1, 3)                      3       True
layers.4.0.bias                     (1,)                        1       True

Total parameters:     52
Trainable parameters: 52
```

Note `layers.2.0.weight` — index `2` selects the third `Sequential` block out of the `ModuleList`, and `0` selects the `Linear` (index 0 inside that `Sequential`; `GELU` at index 1 has no parameters at all, so it never appears in this listing).

## 9 — Two More Patterns: `register_buffer` and `model.apply()`

**`register_buffer`.** Not every tensor a module needs is a trainable parameter. A causal attention mask or a precomputed sinusoidal position table needs to move with the model (`.to(device)`) and get saved in `state_dict()`, but should never receive a gradient or get touched by the optimizer. `register_buffer` is exactly this: a tensor tracked like a parameter for device/serialization purposes, but excluded from `.parameters()`.

```python
class ToyBlock(nn.Module):
    def __init__(self, size):
        super().__init__()
        mask = torch.triu(torch.ones(size, size), diagonal=1).bool()
        self.register_buffer("causal_mask", mask)  # not a Parameter, not trainable

block = ToyBlock(4)
print("In parameters():", any(True for _ in block.parameters()))
print("In state_dict():", "causal_mask" in block.state_dict())
```

```
In parameters(): False
In state_dict(): True
```

**`model.apply(fn)`.** Walks every submodule in the tree (depth-first) and calls `fn(submodule)` on each one — the standard way to apply an initialization rule across an entire network without writing a manual recursive loop.

```python
def init_weights(module):
    if isinstance(module, nn.Linear):
        nn.init.xavier_uniform_(module.weight)
        nn.init.zeros_(module.bias)

model = ExampleDeepNeuralNetwork([3, 3, 3, 3, 3, 1], use_shortcut=True)
model.apply(init_weights)  # re-initializes every nn.Linear inside every nn.Sequential inside the ModuleList
```

`apply` doesn't care how deeply a `Linear` is nested — three levels deep inside a `ModuleList` of `Sequential` blocks is no different from a top-level attribute, because `apply` recurses through `.children()` regardless of which container type is in between.
