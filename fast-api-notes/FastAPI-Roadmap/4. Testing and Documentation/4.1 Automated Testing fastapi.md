# 4.1 Automated Testing in FastAPI

## Overview

FastAPI provides excellent testing capabilities built on Starlette's testing framework. Testing is essential for maintaining reliable APIs and ensuring your endpoints work as expected.

## Key Testing Components

### 1. TestClient

- **What it is**: FastAPI's built-in testing client based on `httpx`
- **Purpose**: Simulates HTTP requests to your FastAPI app without running a server
- **Import**: `from fastapi.testclient import TestClient`

```python
from fastapi.testclient import TestClient
from myapp import app

client = TestClient(app)
response = client.get("/users")
assert response.status_code == 200
```

### 2. Testing Setup with pytest

- **Installation**: `pip install pytest pytest-asyncio`
- **Configuration**: Use `pytest.ini` or `pyproject.toml` for settings
- **Fixtures**: Create reusable test components with `@pytest.fixture`

## Essential Testing Patterns

### Basic Endpoint Testing

Test all HTTP methods your API supports:

- **GET requests**: Test data retrieval, query parameters, path parameters
- **POST requests**: Test data creation, request body validation
- **PUT/PATCH requests**: Test data updates, partial updates
- **DELETE requests**: Test data deletion, proper status codes

### Status Code Testing

Always verify correct HTTP status codes:

- `200` - Success
- `201` - Created
- `400` - Bad Request (validation errors)
- `401` - Unauthorized
- `403` - Forbidden
- `404` - Not Found
- `422` - Unprocessable Entity (Pydantic validation)

### Request/Response Testing

- **Path Parameters**: Test with valid/invalid IDs, data types
- **Query Parameters**: Test optional params, validation rules, defaults
- **Request Bodies**: Test JSON validation, required fields, data types
- **Response Models**: Verify response structure matches Pydantic models

## Authentication Testing

### Token-Based Authentication

- **Login Flow**: Test credential validation and token generation
- **Protected Routes**: Test with valid tokens, invalid tokens, expired tokens
- **Authorization**: Test role-based access control

```python
def test_protected_endpoint():
    # Login to get token
    login_response = client.post("/login", json={"username": "user", "password": "pass"})
    token = login_response.json()["access_token"]

    # Use token in headers
    headers = {"Authorization": f"Bearer {token}"}
    response = client.get("/protected", headers=headers)
    assert response.status_code == 200
```

### Security Testing

- Test endpoints without authentication
- Test with malformed tokens
- Test authorization levels (admin vs user)
- Test token expiration

## Dependency Testing

### Dependency Injection Override

FastAPI allows overriding dependencies for testing:

```python
# Override database dependency
def fake_database():
    return MockDatabase()

app.dependency_overrides[get_database] = fake_database
```

### Common Dependency Tests

- **Database Dependencies**: Use test databases or mocks
- **External Services**: Mock API calls, cache services
- **Authentication Dependencies**: Override user authentication
- **Configuration Dependencies**: Test with different settings

## Database Testing

### Test Database Setup

- **Separate Database**: Use different DB for tests (SQLite in-memory)
- **Transactions**: Rollback after each test
- **Fixtures**: Create test data before tests, clean up after

### Database Test Patterns

- **CRUD Operations**: Test Create, Read, Update, Delete
- **Data Validation**: Test database constraints
- **Relationships**: Test foreign key relationships
- **Transactions**: Test rollback scenarios

## Advanced Testing Techniques

### Parametrized Testing

Test multiple scenarios with `@pytest.mark.parametrize`:

```python
@pytest.mark.parametrize("user_id,expected_status", [
    (1, 200),
    (999, 404),
    ("invalid", 422),
])
def test_get_user(client, user_id, expected_status):
    response = client.get(f"/users/{user_id}")
    assert response.status_code == expected_status
```

### Async Testing

For testing async endpoints and dependencies:

- Use `pytest-asyncio` plugin
- Mark tests with `@pytest.mark.asyncio`
- Test async database operations
- Test background tasks

### Mock Testing

- **External APIs**: Mock third-party service calls
- **Database Operations**: Mock database for unit tests
- **File Operations**: Mock file uploads/downloads
- **Time-sensitive Operations**: Mock datetime functions

## Test Organization

### File Structure

```
tests/
├── conftest.py          # Shared fixtures
├── test_auth.py         # Authentication tests
├── test_users.py        # User-related endpoints
├── test_database.py     # Database operations
└── test_integration.py  # End-to-end tests
```

### Fixture Organization

- **conftest.py**: Global fixtures (client, database, auth tokens)
- **Scoped Fixtures**: `function`, `class`, `module`, `session`
- **Autouse Fixtures**: Automatically run fixtures

### Test Categories

1. **Unit Tests**: Individual functions and methods
2. **Integration Tests**: Multiple components working together
3. **End-to-End Tests**: Complete user workflows
4. **Performance Tests**: Response times and load testing

## Testing Best Practices

### Test Independence

- Each test should be independent
- Clean up test data after each test
- Don't rely on test execution order

### Test Coverage

- Test happy paths (expected scenarios)
- Test edge cases (boundary conditions)
- Test error scenarios (invalid input, failures)
- Use coverage tools to identify untested code

### Validation Testing

- **Input Validation**: Test Pydantic model validation
- **Business Logic**: Test application rules
- **Data Integrity**: Test database constraints
- **Security**: Test authentication and authorization

### Performance Considerations

- Use in-memory databases for speed
- Mock external services
- Parallel test execution
- Optimize test fixtures

## Common Testing Scenarios

### API Endpoint Testing

```python
def test_create_user():
    user_data = {"name": "John", "email": "john@example.com"}
    response = client.post("/users", json=user_data)
    assert response.status_code == 201
    assert response.json()["name"] == "John"
```

### Error Handling Testing

```python
def test_validation_error():
    invalid_data = {"name": "", "email": "invalid-email"}
    response = client.post("/users", json=invalid_data)
    assert response.status_code == 422
    assert "validation error" in response.json()["detail"]
```

### Background Task Testing

```python
def test_background_task():
    response = client.post("/send-email", json={"email": "test@example.com"})
    assert response.status_code == 202  # Accepted
    # Verify task was queued or completed
```

### WebSocket Testing

```python
def test_websocket():
    with client.websocket_connect("/ws") as websocket:
        websocket.send_text("Hello")
        data = websocket.receive_text()
        assert data == "Hello"
```

## Continuous Integration

### GitHub Actions Example

```yaml
name: Tests
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v2
      - name: Set up Python
        uses: actions/setup-python@v2
        with:
          python-version: 3.9
      - name: Install dependencies
        run: |
          pip install -r requirements.txt
          pip install pytest
      - name: Run tests
        run: pytest
```

### Testing in Different Environments

- Test with multiple Python versions
- Test with different database versions
- Test with various dependency versions
- Environment-specific configurations

## Key Takeaways

1. **Use TestClient** for all HTTP endpoint testing
2. **Override dependencies** to isolate tests from external services
3. **Test all HTTP methods** and status codes your API uses
4. **Separate test data** from production data
5. **Mock external dependencies** for reliable, fast tests
6. **Test authentication and authorization** thoroughly
7. **Use parametrized tests** for multiple similar scenarios
8. **Organize tests logically** with clear naming conventions
9. **Achieve good test coverage** but focus on critical paths
10. **Integrate testing** into your CI/CD pipeline
